# Escrow · QAS-01 신뢰성

반품 승인된 100,000원 거래에서 **구매자의 마감 직전 운송장 접수와 자동 판매자 지급이 겹치는 경우**를 구현한다. 브랜치는 `feature/qas-01-reliability`다.

## 실행

Python 3.12 이상과 Node.js가 필요하다. 다음 명령은 저장소 루트에서 실행한다.

```sh
cd backend
uv venv --python 3.12
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

다른 터미널에서 프런트엔드를 실행한다.

```sh
cd frontend
npm ci
npm run dev
```

[데모 화면](http://localhost:3000) · [API 명세](http://127.0.0.1:8000/docs). 프런트엔드는 `/api` 요청을 백엔드로 전달한다. 백엔드 주소는 `BACKEND_URL`로 변경할 수 있다.

## 데모 흐름

1. 반품 승인 거래를 생성한다. 실제 72시간을 기다리지 않도록 승인 안내 게시 시각을 앞당겨 마감까지 15초인 거래를 만든다.
2. 마감 전에 `VALID-001`을 접수한다. 즉시 ‘운송장 확인 중’이 표시되고, 3초 뒤 ‘반품 진행’이 된다. 마감과 확인이 겹쳐도 판매자 지급은 보류된다.
3. 반품 도착을 누르면 모의 택배사의 도착 기록을 반영하고 구매자 환불을 한 번 실행한다.
4. `INVALID-001`과 `WRONG-001`은 운송장 무효·수취인 불일치다. 다른 유효·확인 중 접수가 없으면 마감 후 판매자에게 지급한다.
5. `TIMEOUT-001`은 응답 없음이다. 총 3회 조회하고, 조회 사이에는 1초를 기다린다. 한도에 이르면 ‘담당자 확인 필요’로 지급 보류를 유지한다. 횟수·간격은 데모 설정값이다.
6. ‘100건 검증’은 접수 시각을 마감 50ms 전으로 고정하고 오래된 거래 상태로 지급을 시도하는 경합을 재현한다. 택배 응답은 실제 3초 지연시킨다.

## 검증

```sh
cd backend
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m app.benchmark
```

100건 검증의 목표는 판매자 지급 지시·모의 은행 지급 각 0건, 지급 보류 100건, 마감 후 모든 보류 결정 200ms 이내다. 접수와 마감의 업무 시각은 통제하며, **공통 마감 처리 시작부터 각 보류 결정 완료까지 실제 경과 시간**을 잰다. 앞선 거래 처리 대기 시간도 포함한다. 이 수치에는 HTTP 전송과 운영 스케줄러 지연은 포함되지 않는다. 별도 통합 테스트가 실제 시계의 마감·자동 실행·3초 택배 대기 중 보류 결정을 검증한다.

## 구현 범위

기존 Next.js·FastAPI 골격에 SQLite 영속화와 동일 백엔드의 자동 실행을 연결했다. 순수 정책, 거래 조정, DB·외부 포트를 나누는 레이어드 모놀리스다. 거래 등록·참여·입금 확인 등의 전체 UC는 이 브랜치의 범위에 포함하지 않는다. 시작 상태는 반품이 이미 승인되어 대금이 보류된 거래다.

DB 기본 위치는 `backend/data/escrow.sqlite3`이고 `ESCROW_DB_PATH`로 바꿀 수 있다. 접수·기한·지급/환불 지시·모의 은행 이체가 저장되므로 프로세스를 다시 실행해도 유지된다. 택배 대기 작업은 30초 점유 기한 후 인계할 수 있다. 운송장 접수는 DB 쓰기 트랜잭션 안에서 서버 시각으로 확정한다. 사용자가 보내는 시각으로 기한을 우회할 수 없다.

은행과 택배는 모의 구현이다. `buyer-demo`·`seller-demo`는 시연용 참여자 식별자이며 로그인 인증을 대신하지 않는다. 거래 목록·거래 생성·택배 도착·검증 API는 로컬 시연용이다. 담당자 확인 목록까지 제공하고 수동 판정 UI는 구현하지 않는다.
